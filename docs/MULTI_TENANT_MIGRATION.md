# TradeMind 多租户数据库迁移

更新时间：2026-10-25。迁移由 `backend/internal/database` 启动流程执行。生产执行前必须按本文完成备份与预演；本地测试成功不表示生产迁移已获准或已演练。

## Schema 和回填

迁移扩展 `tenants`、`tenant_memberships`、`tenant_invitations`、`platform_operators` 等模型，并为已有业务任务、文件、导出及 AI 批次等租户记录使用当前模型需要的 `tenant_id` 和索引。实现沿用 GORM AutoMigrate 及当前数据库启动顺序，没有新增独立版本化 SQL migration 框架。

回填原则：

- 保持既有用户 UUID、密码哈希和业务主键；不删除业务行。
- 旧 `admin_users.tenant_id > 0` 用作兼容 membership/旧租户注册证据；tenant 0 不转成任意新客户租户。
- 可从同一店铺、商品、订单、批次、创建者等持久化证据唯一确定归属时才填充业务行。
- 证据相互冲突、缺失或无法唯一确定时，保留 tenant 0；租户用户不可见，需后续受控调查，不能批量猜测归属。
- 原有角色值只在有效角色或合规自定义角色范围内迁移；未知历史角色采用只读失败关闭兼容策略。
- membership 回填可重复执行，唯一约束阻止重复 `(tenant_id,user_id)`；PostgreSQL 回填既有 ID 后会同步 tenants 自增序列，避免之后新租户 ID 冲突。
- 租户字段回填函数使用事务处理本次回填语句；整个应用启动迁移链包含多项 AutoMigrate 和后续迁移，**不保证整体处于一个可回滚事务中**。

## 生产迁移前检查

1. 在与生产版本、PostgreSQL 主版本及数据规模相符的隔离环境恢复备份，先运行当前分支迁移并验证重复启动行为。
2. 统计旧用户 tenant 分布、tenant 0 业务行、关联店铺/商品/创建者冲突、孤立外键式引用、目标表估算行数和索引构建耗时；输出中不得包含凭据或个人敏感字段。
3. 审核回填证据规则；不得为降低 tenant 0 数量而把未知数据指派给 owner 或首个租户。
4. 由运维评估迁移期间写入、锁等待、磁盘空间和备份保留策略，安排维护窗口；生产数据不得作为普通开发测试库。
5. 确认备份能够恢复，并保存数据库版本、镜像 SHA、迁移日志、行数核对和审批记录。

## 执行后核对

- 每个现存非零 tenant 用户都有预期 membership，既有账号 ID 和认证材料未改变。
- tenants 的最大 ID 与 PostgreSQL 生成序列匹配；测试一次独立隔离租户创建只在预生产执行。
- 高价值业务表迁移前后行数及抽样主键一致；未能证明归属的记录仍为 tenant 0。
- tenant 0 不向非零用户暴露；各 tenant 的产品、店铺、订单、任务和文件归属抽样无跨租户引用。
- 登录、角色、店铺权限、租户切换、暂停后撤权、Worker 恢复和数据库 readiness 正常。
- 审计和安全日志无敏感 token、密码或凭据。

## 回滚与恢复

本迁移不提供删除租户列或反向猜测历史归属的自动 downgrade。不要通过回滚应用镜像来假设数据库会回退，也不要删除 tenant/membership/审计记录来“清理”失败迁移。

如迁移失败或产生异常：停止继续 rollout 和业务写入，保留日志及变更记录，依据已审批的恢复方案从一致时间点备份/PITR 恢复数据库及配套对象存储；确认版本与数据一致后，再决定应用版本。先在隔离恢复副本验证完整性，未完成恢复演练前不得宣称已有可用回滚路径。
